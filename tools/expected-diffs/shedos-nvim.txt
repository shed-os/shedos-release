# What may differ between the monolith's shedos-nvim and the one shed-os/shedos-nvim
# builds. Nothing here is a free pass: each path was opened and read before it was
# written down, and an entry that stops matching fails the run.

# Everything below is one cause. materialize-plugins.sh stages the plugin set under
# work=$(mktemp -d), so blink.cmp's cargo build runs in a directory with a different
# absolute path on every build, and cargo writes that path into everything it leaves
# behind. The bytes of the shipped library are the same; only the recorded paths move.
#
# None of these can be pinned: the path is new on every build, so a pinned pair would
# go stale on the next one. They are also not the packaging being wrong twice — they
# are the packaging shipping a build directory it has no reason to ship. Both the
# entries and the ~40MB they cover disappear the moment the build stages into a fixed
# directory, or drops target/ from the package and keeps the one library it needs.
