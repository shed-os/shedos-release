# What separates shed-os/shedos-nvim from the monolith it came out of. Nothing here is a
# free pass: each path was opened and read before it was written down, and an entry that
# stops matching fails the run.
#
# This is a tree-form enumeration: every path is written the way the carved repository
# holds it and every `content` line is pinned <monolith blob>..<carved blob>. What it
# governs is the source. The two builds' bytes are a separate question, asked on demand
# with tools/build-reference.sh; the answer this repository got is kept at the end of this
# file rather than carried as an allowlist that goes stale on the next rebuild.

# --- (a) where the content came from ----------------------------------------------
#
# Source package: shedos-nvim — the preprovisioned Neovim: a runtime under
# /usr/share/shedos/nvim, a thin shim in /etc/skel, the preprovision tool and its user
# unit, and materialize-plugins.sh, which stages the locked plugin set at build time.
# Carve map: tools/carve-maps/shedos-nvim.paths, two directives — `flatten
# packaging/shedos-nvim`, so the packaging directory is the repository root, and `path
# test/nvim/`, which keeps the suite where the pipeline's `test/*/run.sh` looks for it.
#
# 25 package files carve with the two suite files. The carve took both directories as the
# monolith held them at 4f06e3ff, and the comparison below is against 8ce1763e, which is
# where the monolith stands now.

# --- the artifact comparison, kept as history ---------------------------------------
#
# Run once, before this file took its tree form, and it found 84 differing paths, every
# one of them inside usr/share/shedos/nvim/plugins/blink.cmp/target: 47 dep-info files, 46
# of them under target/release/deps and one at target/release/libblink_cmp_fuzzy.d; 22
# build-script outputs under target/release/build, ten of which are dep-info of their own;
# 9 cargo fingerprints; five compiled artifacts, two rlib and two rmeta and one shared
# library, all under deps; and .rustc_info.json at the top.
#
# All 84 are one cause. materialize-plugins.sh stages the plugin set under
# work=$(mktemp -d), so blink.cmp's cargo build runs in a directory with a different
# absolute path on every build, and cargo writes that path into everything it leaves
# behind. The bytes of the shipped library are the same; only the recorded paths move.
# None of them could be pinned — the path is new on every build, so a pinned pair would go
# stale on the next one — which is exactly the kind of expectation this file no longer
# carries.
#
# They are also not the packaging being wrong twice. They are the packaging shipping a
# build directory it has no reason to ship: roughly 40MB of cargo scratch inside the
# package. Both the differences and the 40MB disappear the moment the build stages into a
# fixed directory, or drops target/ from the package and keeps the one library it needs.
# That is still open work, and it is why the finding is written down here rather than
# left in a list of allowlisted paths nobody reads twice.
