# --- (b2) the 8 files with no monolith counterpart --------------------------------
#
# PKGBUILD — the package that did not exist. It builds from this repository's own tag like
# every other carved repo, and installs the library, the nine job modules at
# /usr/lib/calamares/modules, settings.conf and the module confs at /etc/calamares, and the
# branding bundle at /etc/calamares/branding/shedos — the layout the ISO build stages by hand
# today, path for path, except for the library root. See the correspondence below.
#
# The module directories and the branding bundle both install whole, by walking the tree
# rather than by naming files. A module that later grows a helper or a schema would otherwise
# be staged by the ISO build's rsync and dropped by the package, which is the failure the
# house has already met once with a shedman verb missing from a PKGBUILD array. __pycache__
# is the one exclusion, and it is the same one the rsync makes.
#
# shedos_installer/driver_stack.py — the reader for shedos-system's list, and the only new
# library module. It refuses an empty answer: a caller that installs nothing leaves an NVIDIA
# box on modesetting and one that removes nothing leaves the whole stack on a machine with no
# NVIDIA card, and both are silent.
#
# tests/test_driver_stack.py — four cases for that reader: file order, comments and blank
# lines, a missing file, a file naming nothing. Each was watched failing under a mutation of
# the thing it checks.
#
# test/install-paths/run.sh — the PKGBUILD's install root and both modules' INSTALLER_ROOT
# have to agree, and the library the build collects has to be a python package in this tree.
#
# test/shared-data/run.sh — the two files this code reads from other packages, asked of the
# installed system: pacman has to say shedos-system owns the driver stack and shedos-branding
# owns the wallpaper, and the library has to read the whole list out of the real file.
#
# Repository scaffolding the carve could not bring and the package does not ship: README.md,
# .gitignore, .github/workflows/ci.yml.

# --- what the package replaces, path for path ---------------------------------------
#
# The ISO build stages all of this by hand today (Makefile:360-391). The package installs the
# same files at the same paths, with one move:
#
#   installer/shedos_installer/          → /usr/lib/shedos-installer/shedos_installer/
#                                          (the ISO stages it at /opt/shedos-installer/)
#   installer/calamares/modules-src/     → /usr/lib/calamares/modules/         (same path)
#   installer/calamares/settings.conf    → /etc/calamares/settings.conf        (same path)
#   installer/calamares/modules/*.conf   → /etc/calamares/modules/             (same path)
#   installer/calamares/branding/shedos/ → /etc/calamares/branding/shedos/     (same path)
#
# THE TWO CANNOT BOTH BE LIVE. The profile's airootfs is laid down before pacstrap runs, so a
# file staged into airootfs at a path a package also owns fails the ISO build with "exists in
# filesystem" — the Makefile says so itself about /etc/os-release (:366-368). The ISO build
# installing this package and the Makefile staging these files is the same collision, and the
# staging has to go in the same change that adds the package to the ISO's package list.
# Nothing collides today: the ISO does not install this package and the monolith does not
# build it.
#
# The branding version is the sharp edge of that change and is named here rather than solved:
# the Makefile rewrites four version fields in branding.desc after staging it
# (Makefile:382-386), and a packaged branding.desc carries no ISO version to rewrite. Where
# that stamp comes from once the file is package-owned is an ISO-build question.

#    (build-packages.yml:240-246). Both are name matches against a list the monolith reads,
#    so the entry changes nothing the monolith does today — it builds no package by that name
#    — and it is what those two exclusions will read when the ISO build carries it.
#
# 2. The Makefile's `cp -r packages` staging is gone. It copied the whole repo-root
#    packages/ tree under /opt/shedos-installer for config.py's PACKAGE_DIR, and nothing ever
#    read that constant.
#
# BOTH LANDED, on the owner's ruling, as 62818cff and 204fde5b. Each is byte-identical to the
# draft it was gated on. The monolith moved 7b7223a3..8ce1763e with them and one commit of its
# own; nothing in that range touches a path this repository holds.
#
# shedos-release's OWN copy of installer-only.txt must NOT gain the name, and that is not an
# oversight: the publisher refuses to sign anything on that list (publish.sh:69-77), and this
# package publishes to staging like every other carved package until the ISO build takes it
# over. The two copies disagree on purpose until then. What the ISO build reaches for
# afterwards — a channel this list forbids, or the build artifact directly — is a question
# for whoever wires the ISO, and it is open.

# --- parity ------------------------------------------------------------------------
#
# The monolith builds no shedos-installer, so the maps file says `new-package
# shedos-installer` and test/version-parity pairs this repository with nothing. The first cut
# was pkgver 2026.08.09 — the current stable date — with pkgrel 1, the same scheme shedman,
# shedos-theme-engine and shedos-theme-catppuccin took.
#
# What the channel carries is 2026.08.09.1-1. The first release had published when a review
# found the module loop naming files, and a published tag does not move: the fourth component
# is the house form for a second cut of a date-versioned package, established when shedman
# took 2026.08.13.1. `vercmp 2026.08.09.1 2026.08.09` is 1, so the new release supersedes the
# old one rather than sitting under it, and the publisher replaced the entry rather than
# adding one.
#
# There is no version floor on shedos-system, and the reason is worth writing down: what this
# package needs from it is a FILE, and the monolith's shedos-system and the carved one carry
# the same pkgver. A pkgrel floor would not hold either — the monolith's pkgrel moves on any
# change to that package, so it would be satisfied by a build that ships no driver-stack file
# at all. test/shared-data asks the installed package for the file instead, which is the only
# form of the question that cannot be answered by a version number.

# --- the deviation from "generated", stated plainly ---------------------------------
#
# §5.5 says the driver stack is "generated from a shared data file shipped by shedos-system",
# and this reads the file at runtime instead. Generating it into the package at build time
# would put the thirteen names back into a shipped artifact, and an ungenerated build would
# ship an empty list — which installs nothing on an NVIDIA box and strips nothing from a
# machine without one, silently, on the installed system. Reading it makes the drift
# impossible rather than checked, gives the module the same override nvidia-reap already
# takes, and turns the missing-file case into a job that fails with a reason.
#
# The check §7 asks for is real and it is test/shared-data: the file has to exist, pacman has
# to say shedos-system put it there, and the library has to read every name out of it.
